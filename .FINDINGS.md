- **Fix** (your approach and why it is safe)

Group by Backend / Frontend / Cross-cutting.

## Backend

### Issue: Unsafe SQL query allowed user input to directly modify database query

- Where: listProducts in Products Repository
- Why: User input was inserted directly into SQL string instead of using parameters
- Impact: Critical security risk, possible database leak or data damage
- Fix: Replaced string interpolation with parameterized query ($1) so input is treated as data only
- Trade-offs: Slightly more structured code, no performance downside


### Issue: Admin routes were open to anyone without access control, allowing any user to create or update products.

- Where: POST /products and PATCH /products/:id routes
- Why: No backend check for admin token before allowing requests
- Impact: Unauthorized product changes, price and stock manipulation, data corruption 
- Fix: Add middleware that checks ADMIN_TOKEN from request headers before allowing access
- Trade-offs: Uses single shared token, no individual admin tracking or roles

### Issue: Product stock could become negative during updates

- Where: decrementStock in productRepository
- Why: Stock is reduced without checking if enough quantity exists
- Impact: Overselling products, incorrect inventory values, order inconsistencies
- Fix: Update query to only subtract stock if enough quantity exists (stock >= quantity)
- Trade-offs: Must handle “out of stock” response in application logic

### Issue: Missing Transaction Scope During Order Creation 

-What: Stock updates and order creation were happening outside a transaction
- Where: createOrder() in ordersService
- Why: withTransaction() existed but was not used around stock deduction and order creation logic
- Impact: Overselling, partial order creation, inconsistent inventory data
- Fix: Wrapped stock locking, stock deduction, and order creation inside withTransaction() using BEGIN, COMMIT, and ROLLBACK
- Trade-offs: Slightly longer DB connection usage during checkout flow


### Issue: Unsafe PATCH Update Logic where Update logic could behave incorrectly when fields are missing

- Where: updateProduct in productRepository
- Why: All fields were mixed using COALESCE which caused unclear update behavior
- Impact: Wrong data updates, accidental overwrites, inconsistent product data
- Fix: Build dynamic update query that only updates fields actually sent
- Trade-offs: Slightly more code complexity


### Issue: Race Condition During Stock Updates

- What – Multiple users could buy the same stock at the same time
- Where – Product stock validation and decrement flow in createOrder()
- Why – Product was fetched normally without row locking before stock update
- Impact – Overselling, negative stock, incorrect inventory values
- Fix – Use getProductByIdForUpdate() with FOR UPDATE inside transaction to lock product row during checkout
- Trade offs – High traffic products may experience short lock waits under heavy concurrency

### Issue: Duplicate Payment/Webhook Processing

- What – Same payment webhook or retry request could be processed multiple times
- Where – chargeOrder() and processPaymentWebhook()
- Why – No proper duplicate event validation before creating payments or updating orders
- Impact – Duplicate payments, repeated order updates, inconsistent payment records
- Fix – Add idempotency checks using Redis cache and DB uniqueness checks before processing payment/webhook
- Trade offs – Redis dependency added for retry handling consistency


### Issue: Missing Webhook Event Uniqueness

- What – Same payment event could be stored multiple times
- Where – payment_events table
- Why – provider_event_id was not unique
- Impact – Duplicate payment event processing and repeated order updates
- Fix – Add UNIQUE constraint to provider_event_id
- Trade offs – Duplicate insert attempts now throw DB errors if not handled properly

### Issue: Missing Idempotency Key Protection

- What – Same payment request could create multiple successful charges
- Where – payments table and chargeOrder()
- Why – idempotency_key existed but was not enforced as unique or fully validated before charging
- Impact – Double charges, duplicate payment records, financial inconsistency
- Fix – Added unique constraint on idempotency_key and checked existing payments before charging again
- Trade offs – Client must always send valid idempotency key for retries

### Issue: Client-Controlled Order Total

- What – API trusted frontend totalAmount value during order creation
- Where – createOrder()
- Why – Total amount was passed directly from client instead of calculated from product prices in DB
- Impact – Price tampering, underpayment risk, financial inconsistency
- Fix – Removed client-provided total and calculated total securely using DB product prices
- Trade offs – Slightly more backend processing during checkout

### Issue: Missing Default Order Status

- What – Orders required manual status assignment during creation
- Where – orders table schema
- Why – No default value for order status
- Impact – Invalid or missing order states if application forgets status
- Fix – Add default status 'PENDING' at DB level
- Trade offs – Application must still update status correctly during payment lifecycle

### Issue: Invalid Order Item Validation

- What – Invalid quantities or malformed order items could pass into order flow
- Where – createOrder()
- Why – Missing validation for quantity and item structure
- Impact – Invalid orders, broken inventory logic, bad data storage
- Fix – Add validation for productId, quantity, and quantity minimum checks before processing
- Trade offs – Slightly stricter request validation for frontend clients

### Issue: Product list returned all records at once

- Where: listProducts in productRepository
- Why: No limit or offset used in query 
- Impact: Slow API, heavy database load, poor frontend performance
- Fix: Add pagination using LIMIT and OFFSET
- Trade-offs: Frontend must handle paginated responses


### Issue: No sku uniqueness, same sku could be created multiple times

- Where: createProduct in productRepository
- Why: No uniqueness rule enforced in database
- Impact: Duplicate products, inventory confusion, order mismatches
- Fix: Add UNIQUE constraint on SKU in database
- Trade-offs: Insert may fail if duplicate SKU is sent, must handle error properly
